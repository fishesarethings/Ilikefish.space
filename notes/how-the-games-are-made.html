How a small browser game gets made here

Notes · 4 November 2026

Most of the games here are small on purpose. A single mechanic, one screen, a session that fits into a coffee break. That constraint is what makes them quick to load, easy to learn and cheap to keep running.

Start with one mechanic

A game usually begins with a sentence rather than a design document. Swim upstream and shoot obstacles. Drag blocks onto a grid until a line clears. Roll a die, buy a machine that rolls it for you. If the sentence is clear, the first playable version is close.

The temptation is always to add a second idea too early. A shop, a boss, a stamina bar. Those things are easier to add once the core loop is already fun, and much harder to judge while the loop is still moving.

A folder, not a framework

Every game lives in its own folder under /games/. The folder holds the entry page, a config.json with the name, description and icon, and whatever assets the game needs. The entry page is plain HTML, CSS and JavaScript. There is no build step and no bundler: open the file in a browser and it runs.

That choice keeps the site portable. A game can be copied out of the repository, opened on a laptop and still work. It also keeps the pages small, which matters more on a phone than on a desktop.

Test on the thing people actually use

A game that plays well with a mouse can be miserable with a thumb. Every game is checked at a phone-sized viewport, and any game that needs a keyboard is either given on-screen controls or marked as desktop-only in the catalogue. The controls are written down on each game page, because a game that does not explain its controls is a game most people will close.

The other test is the boring one: reload it, resize the window, open it twice, clear the cache. Most of the bugs that survive to release are not gameplay bugs; they are layout and storage bugs.

What gets left out

There are no accounts, no purchases, no loot boxes and no virtual currency that costs money. Progress is stored in the browser. That removes a large amount of complexity from both the game and the page around it.

Unfinished games do not go into the catalogue. A prototype can sit in a folder for months, but it only gets a page, a description and a place in the sitemap when it is actually playable from start to finish.

The Game Maker

The Game Maker is the same idea turned into a tool. It lets you assemble a small game package in the browser: name, slug, description, icon, entry page and any extra files. The output is a folder that can be dropped into a site like this one. It is not a full engine, and it is not trying to be.

Why small is the point

A small game can be finished. That sounds unambitious, but finishing is the hard part. A game that is finished can be tested, described, linked and kept working. A game that is almost finished is a folder nobody can play.

If you make small browser games and want one hosted here, the creator page explains how submissions work.
